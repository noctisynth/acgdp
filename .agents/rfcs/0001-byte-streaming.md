# RFC 0001：尚在写入的内层归档解压

> 状态：Accepted（先实现非 solid 的 7z→RAR 路径）；日期：2026-09-29

## 现状与目标

原有 `--jobs 2` 在外层条目完整写出后才把它交给内层工作线程。用户的单链大包通常只有一个巨大的内层条目，因而该模式无法重叠这两层的解压。目标是在外层仍写入该条目时，内层安全地消费已写出的字节，并以实际大文件基准证明端到端收益。失败时仍不得交付部分结果，原始输入仍须不变，累计写出预算仍须跨层共享。

## 格式差异与样本证据

- ZIP 的中央目录通常在尾部，`zip` 现有读取器需要完整归档才能列出条目。需另行验证以本地文件头逐项读取的能力、数据描述符、加密和伪装前缀。
- 7z 当前读取器需要 [`Read + Seek`](https://docs.rs/sevenz-rust2/latest/sevenz_rust2/struct.ArchiveReader.html) 来解析归档索引；虽能流式解码已知条目，内层 7z 的索引可能在尾部。不能把“可流式写出”直接等同于“可提前打开尚未完成的归档”。
- RAR 当前 `unrar-ng` 接收文件路径。[UnRAR API 源码](https://github.com/pmachapman/unrar/blob/master/dll.cpp) 可按路径在共享模式下打开正在下载的归档，但 [API 头文件](https://github.com/pmachapman/unrar/blob/master/dll.hpp) 没有通用的自定义输入读取回调。真实样本的内层是带 JPEG 前缀、加密文件头的 RAR5，外层只有这一项；实测结果见[样本验证](../spikes/0002-real-split-archive.md)。

## 候选方案

1. **按格式逐步实现**：先在可验证的 ZIP 子集做顺序流读取，遇到不支持的中央目录、加密或数据描述符形式则回退到完整文件路径；再独立验证 7z 和 RAR。优点是安全边界可分格式证明，缺点是不能立即加速真实 RAR 样本。
2. **增长文件加阻塞读取视图**：外层写入时让内层读取器等待缺失字节。需确认每个后端不会把暂时 EOF 当成损坏，且 seek 到尾部、文件长度缓存与超时取消均有明确定义。当前 `unrar-ng` 的路径接口不能直接注入这个视图。
3. **替换或扩展 RAR 后端**：原型验证 UnRAR 共享模式或具备读取回调的其他后端，并重新审查许可、跨平台构建、加密 RAR5、伪装前缀及路径安全。只有通过这些验证后才进入 Active Spec。

## 验收方式

为每种支持的格式构造外层慢速写入、内层多 GB 单链包，包含加密、图片前缀、截断、坏密码、取消和磁盘不足。以 Criterion 或等效的交错配对测量比较 `--jobs 1`、现有条目级 `--jobs 2` 与新模式；记录首个最终字节出现时间、总时间、CPU、磁盘峰值和输出一致性。真实 `PC16751` 样本须有同机串行与新模式对照，才能宣称其受益。

## 已选方案与后续问题

已用真实样本验证：JPG 仅写出 64 MiB 时，UnRAR 能提取第一个完整条目；之后会在当前文件末尾返回 `EndArchive`，此时外层仍在写入。选定做法是等待文件增长、重新打开非 solid RAR，跳过已成功提取的条目并继续，直到外层完成且 RAR 正常结束。无需更换 RAR 后端。solid RAR、ZIP 与内层 7z 仍按完整文件处理；这些格式需要后续独立验证。
