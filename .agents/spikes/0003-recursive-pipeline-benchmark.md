# 递归多层流水线提交前基准

> 日期：2026-09-29；Windows，Rust 1.98.1；发布优化编译

## 对照与夹具

基线为提交 `3295e3b` 的发布版可执行文件；候选版在同一源码与依赖上把流水线递归应用于每个嵌套层。`tests/compare_pipeline.py` 在同一目录中生成确定性的 16 MiB 内容，以 ABBA/BAAB 顺序交错调用两版二进制，每个场景各运行 16 次。计时包括进程启动、解压、扫描、输出交付和删除临时结果。

| 场景 | 基线中位数 | 候选中位数 | 候选/基线 |
| --- | ---: | ---: | ---: |
| 两层单链 ZIP | 0.204 秒 | 0.205 秒 | 1.005 |
| 多个内层 ZIP 与大型普通文件 | 0.861 秒 | 0.864 秒 | 1.003 |
| 四层 ZIP 链，每层有普通文件 | 0.787 秒 | 0.780 秒 | 0.991 |

三组配对中位数差异均约 1% 以内，无法据此证明加速或回归。四层夹具里的每个内层 ZIP 仍须完整写出才能开始下一层；一边处理嵌套包、一边写出同层后续普通文件时，递归调度才有重叠机会。此夹具不代表多层加密 7z/RAR 的 CPU 与磁盘特性。

完成所有源码与用户文档改动后，再次发布构建并交错运行 12 次/版本：单链为 0.115/0.113 秒（基线/候选），多内层为 0.637/0.624 秒，四层为 0.985/1.016 秒。对应比值为 0.987、0.980、1.032。四层两轮的差异方向相反，幅度约 1–3%，因此不能声称稳定提速，也没有可靠证据表明这次改动造成明显回归。

同一改动也运行了 `cargo bench --bench nested_extraction -- --noplot`，加入四层链后各组 10 个 Criterion 样本。先测基线、后测候选时，连未修改的 `--jobs 1` 串行四层组也从 703.51 ms 变为 393.83 ms，约差 44%；可见这两轮受缓存或后台负载影响，不能直接按 Criterion 的跨轮百分比评价代码变化。因此以上交错对照是本次主要的回归检查。

## 真实分卷样本

相同 `PC16751.7z.001/.002`、密码和 `--max-gib 8` 下，候选版一次完成于 239.84 秒，随后基线版一次完成于 668.06 秒。基线版在此前环境下曾完成于 262.10 秒，说明真实样本波动远大于小夹具；不能把这次差值归因于递归调度。两次结果均有 24,834 个文件，按相对路径与大小比较完全一致，共 1,453,416,343 字节。之前的基线结果已做全文件 SHA-256 校验；本次新结果尚未做逐文件哈希。

## 结论与后续

递归阶段调度的正确性由四层 ZIP 和第二层 7z→第三层 RAR 冒烟测试覆盖；交错基准未观察到明显性能回归。收益需在代表性大文件上增加多轮交错测量，最好分开记录外层解码、格式扫描、RAR 重开、最终合并及磁盘等待时间。单链连续 ZIP 或内层 7z 仍受完整文件格式边界限制；这属于格式后端能力，不是调度层可单独消除的等待。
